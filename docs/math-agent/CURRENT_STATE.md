# Math Agent — Current State

Last updated: 2026-10-06

## Existing Product

The previously described mathematics community website contains problem pages, solution pages, an AI side panel, user-configured API access, similar-problem recommendation, scratch space, LaTeX input, and handwriting capability.

The current AI system is primarily chat-oriented rather than a complete Math Agent. This repository now contains both the application source and the authoritative Math Agent documents. The active specifications are target architecture, not evidence that each component is built.

## Active Delivery Phase

The main **Phase 1 UI skeleton** is present for the current text-based actions and the selected-handwriting confirmation entry. **Phase 2 minimum functional loop is partial**: the visible flows use local state and a model relay, but lack a general mathematical verifier, durable Agent Session and live-provider acceptance results. The route map and teach-back are isolated Phase 3 experiments, not completed pedagogy or learner-model services.

```text
UI skeleton
→ minimum functional loop
→ pedagogy strategy
→ complete Context Engine
→ long-term learning Agent
```

Capabilities without a corresponding user-facing UI action should remain specifications, interfaces, and TODOs by default. Existing foundations are preserved, but architecture depth is not the current success criterion.

## Target Migration

```text
AI Chat → Math Copilot → Math Agent
```

The Agent should understand Problem Context, Solution Context, Selected Step, User Attempt, Hint State, and Learning Preferences, and invoke Math Tools, Visualization, Verification, Hint System, and Similar Problems.

## Minimal Hints from a Submitted Draft (2026-09-27)

The first narrow Stage 4 loop is implemented: “基于这版草稿给最小提示” beside the draft editor, plus explicit natural-language requests such as “基于这版草稿给最小提示”. Inspection found that ordinary hint requests omitted attempts, while any attached attempt triggered diagnosis rendering, provider JSON parsing and arithmetic-result composition. Draft hints now use the hint intent with a separate validated draft target and renderer; diagnosis-only execution remains gated to diagnosis. A hint never directly displays the verifier's corrective answer.

`draftHint.js` requires a submitted current-problem attempt, exact agreement with the lower editor, enabled context sending, current image/ink provenance and renewed reading confirmation. A newly selected but unconfirmed image cannot silently reuse another confirmed image's attempt. Unsubmitted edits, reading changes, stale sources and restored-but-unconfirmed images produce an actionable notice without a provider call. This entry also accepts submitted typed drafts; it does not submit a new version merely by asking for a hint.

Explicit draft actions replace an unrelated reference-step focus. Context prioritizes the current attempt over that selection and omits reference answers/solutions, original images, OCR candidates/excluded blocks and old diagnosis messages. The prompt contains only the current problem, submitted steps, scoped arithmetic statuses and existing reveal state. Arithmetic statuses do not prove earlier reasoning or the whole route, and no verifier explanation/corrective answer is passed as a ready-made hint. The provider is asked to identify the earliest relevant obstacle, preserve a viable learner route and propose one small action. This remains a preliminary model judgment, not a verified pedagogical diagnosis.

Draft hint messages/actions carry `attemptRef`. “再提示一点” on that hint, and subsequent hint requests while that draft-hint target remains current, reuse the same current-draft entry. Editing cancels an in-flight draft hint; version/source/reading changes expire old feedback and disable its continuation action. Retry rebuilds from the latest valid submitted attempt. Explicit full-solution requests keep the existing available solution path. Natural-language routing is anchored to affirmative draft-target requests; a request saying not to use a draft is not misclassified as draft-hint authorization.

The existing problem/focus HintState and displayed-reveal checkpoint are reused, not reset per attempt version. Ordinary draft hints are HintBlocks with an AI-unverified warning. The existing obvious-answer disclosure guard hides recognized answer-bearing replies; hidden replies, provider failures and cancelled/late requests do not advance shown hint progress. Already displayed hints remain recorded across editing and refresh. Progression is still the existing bounded 0–4 ladder (and the existing post-solution behavior), not an adaptive blocker-aware reveal budget or a complete semantic leakage guard.

## Bounded Earlier-Premise Sign Check (2026-09-28)

Gap against 02/03/04/05/09/10: selecting a distant student step as a local-hint premise preserved its source but did not verify its mathematics. LH03 showed that a fabricated model reply could falsely endorse `a-b<0` under the problem's explicit `a>b>0`. The new provider-independent `verify_ordered_difference_sign` tool checks only a single plain-letter difference sign (`a-b>0`, `<0`, or `=0`, including the reversed difference) against a leading `已知 [实数] a>b` or `a>b>0` condition. It returns `valid`, `invalid` or `unknown`, with the checked claim, source assumption and expected sign. Negation, quoted claims, compound student statements, unsupported notation, ambiguous conditions and extra input fields remain `unknown`; this is not an inequality solver or a whole-step proof.

The Context Engine checks the exact student-selected earlier step only after the current submitted attempt, source and local target pass their existing guards. A proven conflict stops before prompt/provider work. The drawer shows a typed tool VerificationBlock naming the one conflicting claim and its assumption, plus an explicit warning that the entire step was not verified. It offers editing that step; no model reply or hint reveal is recorded. The same gate serves the button and natural-language local-hint entries. After correction and a new submitted version, the learner reselects the target and premise; the existing hint flow resumes from its current reveal state. A `valid` or `unknown` tool result does not certify the premise's role in the solution and does not add a broad verified label.

Validation in the original checkout: 168/168 frontend unit tests, including paired LH01–LH04 and tool/response-block boundary cases; `tests/premise-sign.browser.test.cjs` passed the conflict, natural-language parity and corrected-version journey; the existing local-hint, whole-draft-hint, attempt-version and main-assistant browser regressions passed; production build passed.
